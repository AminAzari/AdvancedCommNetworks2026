# Module 17: 3GPP Standardization for Advanced Communication Networks

## 1. What is 3GPP?

The **3rd Generation Partnership Project (3GPP)** is a global collaboration of telecommunications standards organizations that develops technical specifications and reports for mobile communication systems. Founded in December 1998, 3GPP unites seven regional Organizational Partners (OPs) to produce globally applicable standards covering radio access, core network architecture, and service capabilities.

### Organizational Partners

| Partner | Region | Full Name |
|---------|--------|-----------|
| **ETSI** | Europe | European Telecommunications Standards Institute |
| **ARIB** | Japan | Association of Radio Industries and Businesses |
| **ATIS** | North America | Alliance for Telecommunications Industry Solutions |
| **CCSA** | China | China Communications Standards Association |
| **TTA** | South Korea | Telecommunications Technology Association |
| **TTC** | Japan | Telecommunication Technology Committee |
| **TSDSI** | India | Telecommunications Standards Development Society, India |

### Key Characteristics

- **Not a legal entity** — 3GPP is a partnership project governed by its OPs
- **Market Representation Partners (MRPs)** provide industry input (e.g., GSMA, 5GAA, NGMN)
- **Individual Members** are companies participating through their regional OP
- Specifications are **transposed** into regional standards by each OP (e.g., ETSI publishes them as EN/ES/TS)
- Covers **2G (GSM/GPRS/EDGE), 3G (UMTS), 4G (LTE/LTE-A), and 5G (NR)** systems

| Working Group | Responsibility |

| **RAN4** | Radio performance, RF parameters, RRM requirements |
| **RAN5** | UE conformance testing |

| Working Group | Responsibility |
|---------------|---------------|

| **SA4** | Media codecs, streaming, MBMS |
| **SA5** | Management, orchestration, and charging |

| Working Group | Responsibility |

## 3. Specification Types

### 3.1 Types of Documents

| Type | Name | Nature | Purpose |
|------|------|--------|---------|
| **TS** | Technical Specification | **Normative** | Defines mandatory requirements, procedures, protocols |
| **TR** | Technical Report | **Informational** | Documents studies, feasibility analyses, best practices |

- **TS documents** contain "shall" requirements — they define what implementations MUST do
- **TR documents** contain "should/may" language — they inform decisions but are not binding
- TRs often precede TSs (a study item produces a TR, which leads to a work item producing/updating TSs)

### 3.2 Numbering System

The specification number format is: **xx.yyy** (or xx.yyy for series ≤ 13) and **xx.yyy** for all series.

```
  xx  .  yyy
  │       │
  │       └── Specification number within series (001-999)
  └────────── Series number (defines subject area)
```

**Example:** `38.331`
- **38** = 5G NR radio technology series
- **331** = RRC protocol specification

#### Series 00–13: Legacy GSM/GPRS Series (originally numbered without leading digits)

These map to the older GSM specification numbering and are maintained for backward compatibility.

#### Series 21–38: UMTS and Beyond

| Series | Subject Area |
|--------|-------------|
| **21** | Requirements |
| **22** | Service aspects ("stage 1") |
| **23** | Technical realization ("stage 2" — architecture) |
| **24** | Signalling protocols ("stage 3" — UE to network) |
| **25** | UTRAN radio technology (3G) |
| **26** | Codecs |
| **27** | Data (AT commands, etc.) |
| **28** | Signalling protocols ("stage 3" — SS, OAM) |
| **29** | Core network protocols (stage 3 — network-to-network) |
| **30** | Programme management (Rel-4 old numbering) |
| **31** | UICC / USIM / ISIM |
| **32** | OAM&P (management and charging) |
| **33** | Security |
| **34** | UE test specifications |
| **35** | Security algorithms |
| **36** | LTE (Evolved UTRA) radio technology |
| **37** | Radio measurement and protocol conformance (multi-RAT) |
| **38** | 5G NR radio technology |

### 3.3 Stage Methodology (ITU-T approach)

| Stage | Description | Typical Series |
|-------|-------------|----------------|
| **Stage 1** | Service description from user's perspective | 22.xxx |
| **Stage 2** | Logical analysis / architecture | 23.xxx |
| **Stage 3** | Protocol implementation / detailed procedures | 24.xxx, 29.xxx |

## 4. Release System

### 4.1 Release Lifecycle

```
┌──────────┐    ┌───────────┐    ┌────────────────┐    ┌──────────────────┐    ┌─────────────┐
│  Study   │───▶│ Work Item │───▶│   Functional   │───▶│ ASN.1 / Protocol │───▶│ Maintenance │
│  Phase   │    │ Approval  │    │    Freeze      │    │     Freeze       │    │   Phase     │
│          │    │           │    │                │    │                  │    │             │
│ (TR out) │    │ (TS work  │    │ (Feature       │    │ (Encoding/       │    │ (CRs only)  │
│          │    │  begins)  │    │  complete)     │    │  protocol final) │    │             │
└──────────┘    └───────────┘    └────────────────┘    └──────────────────┘    └─────────────┘
```

**Phase Details:**

1. **Study Phase** — Feasibility and technical investigations; output is a TR
2. **Work Item Approval** — PCG/TSG approves; specification drafting begins
3. **Functional Freeze** — All features for the release are complete; no new functionality added
4. **ASN.1 / Protocol Freeze** — Protocol encoding (ASN.1, JSON, etc.) is frozen; only essential corrections
5. **Maintenance** — Only critical bug-fix Change Requests (CRs) accepted

## 5. How to Navigate 3GPP Specifications

### 5.1 Spec-Numbering Convention

Understanding the number tells you immediately what a spec covers:

```
  3GPP TS 23.501 V17.6.0 (2022-09)
  │     │  │  │    │         │
  │     │  │  │    │         └── Publication date
  │     │  │  │    └──────────── Version: Release.Major.Minor
  │     │  │  └───────────────── 501 = 5G System (5GS) architecture
  │     │  └──────────────────── 23 = Stage 2 (architecture) series
  │     └─────────────────────── TS = Technical Specification (normative)
  └───────────────────────────── 3GPP organization
```

**Version numbering:** The first digit of the version maps to the Release:
- Version 3.x.x → Release 99
- Version 4.x.x → Release 4
- ...
- Version 15.x.x → Release 15
- Version 17.x.x → Release 17

### 5.2 How to Find Specifications

| Resource | URL | Use |
|----------|-----|-----|
| Spec Finder | https://www.3gpp.org/specifications/specification-numbering | Search by number |
| Specification series | https://www.3gpp.org/specifications | Browse by series |
| Portal (latest + archive) | https://portal.3gpp.org/ | Advanced search, CR tracking |
| FTP server | https://www.3gpp.org/ftp/Specs/ | Direct download of .zip files |
| Work Plan | https://www.3gpp.org/specifications/work-plan | Track ongoing items |

**Practical Search Workflow:**

1. Go to **portal.3gpp.org** → "Specifications" tab
2. Enter spec number (e.g., "23.501") or keyword
3. Filter by Release and version
4. Download the latest approved version (.docx or .pdf)

### 5.3 Reading a 3GPP Specification

Every 3GPP spec follows a standard structure:

| Section | Content |
|---------|---------|
| **1. Scope** | What the spec covers and does NOT cover |
| **2. References** | Normative and informative references to other specs |
| **3. Definitions and abbreviations** | Precise term definitions; abbreviations list |
| **4. General / Overview** | High-level system description |
| **5+. Technical content** | Procedures, architecture, message flows |
| **Annexes** | Additional information, ASN.1, examples |

**Tips for Reading:**

- Start with **Scope** to confirm you have the right document
- Use **References** to trace dependencies (specs reference each other heavily)
- The **Definitions** section resolves ambiguity — always consult it
- Look for **"shall"** (mandatory), **"should"** (recommended), **"may"** (optional)
- Use Ctrl+F for specific procedure names or information elements

## 6. Study Items vs Work Items

### 6.1 Overview

```
┌────────────────────┐          ┌────────────────────┐
│    Study Item (SI) │          │   Work Item (WI)   │
│                    │          │                    │
│ • Feasibility      │  ─────▶  │ • Specification    │
│ • Gap analysis     │ Approval │   creation/update  │
│ • Solution options │          │ • Normative text   │
│ • Output: TR       │          │ • Output: TS       │
└────────────────────┘          └────────────────────┘
```

### 6.2 Study Item (SI)

- **Purpose:** Investigate feasibility of a new feature or technology
- **Output:** Technical Report (TR) documenting findings, options, conclusions
- **Duration:** Typically 1–4 TSG meetings (9–18 months)
- **Process:**
  1. Company submits SI Description (SID) to TSG
  2. TSG approves the study
  3. Working group conducts the study (contributions from member companies)
  4. TR is produced with conclusions and recommendations
  5. If feasible → WI proposal submitted

### 6.3 Work Item (WI)

- **Purpose:** Create or modify normative specifications
- **Output:** New or updated Technical Specifications (TS)
- **Duration:** Tied to the target Release timeline
- **Process:**
  1. Company submits Work Item Description (WID) based on SI conclusions
  2. TSG approves the WI (assigns to working group, sets milestones)
  3. Working group drafts Change Requests (CRs) to existing specs or new specs
  4. CRs are reviewed, revised, and approved at WG/TSG level
  5. Approved CRs are incorporated into the spec version for that Release

### 6.4 SI → WI Flow Example

```
Example: NR Sidelink Relay (Release 17)

SI Phase (2019-2020):
  └── TR 38.836: "Study on NR sidelink relay"
        └── Conclusions: Relay architectures A and B feasible
              └── Recommended for WI

WI Phase (2020-2022):
  └── WID approved at TSG RAN#90
        └── Updates to: TS 38.300, TS 38.331, TS 38.321, TS 24.587
              └── Feature complete at Rel-17 functional freeze
```

## 7. Practical Guide: Referencing 3GPP Specs in Academic Work

### 7.1 Standard Citation Format

```
3GPP, "Title of Specification," 3GPP TS/TR xx.yyy, Version Vx.y.z, Month Year.
```

**Example (IEEE style):**
```
[1] 3GPP, "System architecture for the 5G System (5GS); Stage 2,"
    3GPP TS 23.501, Version 17.6.0, Sep. 2022.
```

**Example (APA style):**
```
3rd Generation Partnership Project. (2022). System architecture for the 5G System
(5GS); Stage 2 (3GPP TS 23.501 V17.6.0). https://www.3gpp.org/
```

### 7.2 Best Practices

| Do | Don't |
|----|-------|
| ✅ Cite specific version (Vx.y.z) | ❌ Cite without version (specs change every quarter) |
| ✅ Include the Release number | ❌ Assume "latest" is stable |
| ✅ Reference the exact section/clause | ❌ Cite entire 500-page spec without clause |
| ✅ Use official 3GPP document titles | ❌ Paraphrase titles |
| ✅ Include access URL/date for online refs | ❌ Link to unofficial mirrors |

### 7.3 Where to Download for Citation

- **Official archive:** https://portal.3gpp.org/desktopmodules/Specifications/SpecificationDetails.aspx?specificationId=xxxx
- **Direct spec URL pattern:** `https://www.3gpp.org/ftp/Specs/archive/[series]/[spec_number]/`
- Always cite the **approved** version (not drafts or working documents)

### 7.4 Citing Change Requests (CRs) and Contributions

For referencing specific proposals or changes:
```
3GPP TSG RAN WG1, "Title," Tdoc R1-21xxxxx, Meeting #10x, Month Year.
```
